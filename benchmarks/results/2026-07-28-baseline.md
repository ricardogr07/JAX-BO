# Baseline: current unrefactored code, 2026-07-28

Baseline for the refactor, recorded on the current code (branch point
`8685b3a`, jaxbo 0.1.2) on the newest jax this code can run on. jax 0.9.2 is
that ceiling: `jnp.clip(..., a_min=...)` (23 call sites) emits a
DeprecationWarning there and is removed in jax 0.10, and `from pyDOE import
lhs` needs a module-name shim (installed distribution pydoe 1.3.0 exposes
only lowercase `pydoe`).

## Amended after adversarial review

Re-recorded after the adversarial review of PR #42. What changed and why:

- **Fixtures are now 4D** (were 2D), matching the real consumer
  (shelter-pulse `jaxbo_optimizer.py`: 4 budget shares on `[0, 1]^4`,
  `(1, 4)` predict inputs). All numbers changed; the 2D record is in git
  history.
- **New case `train_fresh_instance`**: a new `GP(...)` constructed inside
  every timed round and trained once, mirroring the consumer's fresh GP per
  BO iteration. The old warmed-instance case is kept, renamed
  `train_warm_instance`. The fresh case is the direct gate for issue #30.
- **The EI bench now mirrors the consumer path exactly**: per candidate, a
  `(1, 4)` `gp.predict` with params/batch/bounds only, then
  `acquisitions.EI(mu, std, best)`, then a host `float()`. The fused
  `gp.acquisition` loop is kept as a secondary case.
- **"Cold first call" renamed to "first-call latency"** everywhere; it
  conflates trace + compile + execute (and jax init in a fresh process).
- **The profile section reports first-call composition honestly** instead of
  attributing all of it to instance keying.
- **`profile_train.py` now wraps the profiled call in
  `jax.block_until_ready`**, like the bench timings; artifacts regenerated.
- **Noise band recomputed from the actual run spread**, formula stated
  below; IQR columns included.
- **Four runs instead of three**: run 3 caught a background-load window on
  the train benches (its train IQRs do not overlap any other run's), so a
  fourth run was recorded to adjudicate which machine state is normal.

### Run agreement and noise band

Run 3 caught a background-load window during its train portion (the train
benches run last in the suite): its three warm-train IQRs overlap no other
run's IQR (n=128: [329 .. 421] vs [158 .. 196] everywhere else). Run 4 was
recorded to adjudicate and landed with runs 1 and 2, so runs 1, 2, 4 are the
machine's normal state. Run 3's non-train rows are normal (its EI consumer
median is actually the fastest) and are kept.

**Noise band formula.** Per bench: keep the run medians whose IQR overlaps
at least one other run's IQR (this drops only run 3's three warm-train
rows), then

```
band = (max kept median - min kept median) / baseline
```

| Bench | Kept runs | Band |
|---|---|---|
| train warm instance, n=32 | 1, 2, 4 | 10.3 percent |
| train warm instance, n=128 | 1, 2, 4 | 11.6 percent |
| train warm instance, n=512 | 1, 2, 4 | 14.6 percent |
| train fresh instance, n=128 | all | 25.8 percent |
| predict, 256 points batched | all | 17.8 percent |
| EI consumer path | all | 9.9 percent |
| EI fused acquisition | all | 16.1 percent |

A claimed improvement must exceed its bench's band; below that is noise on
this machine. The fresh-instance band is the widest (compile-heavy, most
sensitive to machine state); the fix issue #30 targets would move that bench
from 654 ms toward the 180 ms warm number, a roughly 72 percent drop, which
clears the 26 percent band with margin.

## Profile: one process-cold GP.train call (n=128, num_restarts=3)

Artifacts: `2026-07-28-train-cprofile.prof` (binary, load with `pstats`) and
`2026-07-28-train-cprofile.txt` (top 40 by cumulative time). Fresh process,
profiled call wrapped in `jax.block_until_ready`, total 2.70 s, 578,767
function calls. cProfile was used instead of jax.profiler to avoid pulling
the TensorBoard UI stack; the hotspots are Python-level anyway.

### First-call latency composition

The 2.70 s process-cold first call decomposes into overlapping buckets
(compile time nests inside the callers that trigger it, so these do not sum
to the total):

1. **XLA backend compilation, 1.464 s (54 percent): 24 separate pjit
   compilations** for one train call (`compiler.py backend_compile`).
2. **About 1.0 s of cumulative time under `random_init_GP`
   (initializers.py)**: the first trace + compile + execute of the
   `jax.random` sampling kernels (`uniform` 0.49 s, `normal` 0.17 s, plus
   the arithmetic on the samples). These live in module-level jax caches,
   not under the GP instance, so they are paid once per process. **No
   instance-cache fix removes this bucket.**
3. **About 1.0 s under the scipy L-BFGS path**: 173 scipy function
   evaluations, 130 `objective()` calls, each crossing the Python -> jitted
   `likelihood_value_and_grad` -> `onp.array` boundary (a device sync per
   step), including the likelihood's own first-call compile. The warm-path
   train cost (179.9 ms median) is this round-trip loop with the compiles
   already paid.

### What this data can and cannot attribute

- **Can:** the instance-keyed share of first-call latency, measured
  directly by the `train_fresh_instance` bench: 654 ms fresh vs 180 ms warm
  in-session, so about **474 ms per fresh `GP(...)`** is re-paid because the
  jitted methods use `static_argnums=(0,)` with default object hashing,
  keying the pjit cache on instance identity. That bench, not this profile,
  is the gate for issue #30.
- **Cannot:** a per-compile split of the 24 pjit compilations into
  instance-keyed vs shared-cache ones; cProfile does not tag cache keys.
  The process-cold 2.70 s therefore must not be quoted as "what the cache
  fix saves": the initializer kernels (bucket 2) and jax's own first-touch
  costs stay regardless of instance keying.

### Structural observations

- The 3 restarts run sequentially through `minimize_lbfgs_grad`; they are
  independent and not vmapped or parallelized, so warm train time scales
  linearly with `num_restarts`.
- The consumer EI path shows the same per-call dispatch pattern: 0.535 ms
  per candidate through two dispatches plus a host sync, vs 1.07 ms for one
  batched 256-point `predict`.
